# Map Building (JS/three.js)

Порт `.claude/rules/map-building.md` (Godot-эра) на web-стек + всё найденное после миграции. Источники истины: `docs/space-kit-terrain-catalog.md` (полный каталог ассетов, построен прямым парсингом GLB — читай его целиком перед любой новой ориентацией/новым ассетом), `web-slice/src/map/mapLoader.ts`, `web-slice/src/map/assetLoader.ts`.

## Формат карты (не изменился с Godot-эры)

Грид 1×1м (`tile_size=1.0`), `level_height=0.5` на уровень. Клетки pivot-centered: клетка с индексом 0 занимает мировой диапазон `[-0.5, 0.5)`. `origin_offset` сдвигает всю карту (обычно так, чтобы центр карты был в `(0,0,0)`).

```json
{
  "meta": {"tile_size": 1.0, "level_height": 0.5, "origin_offset": [-N/2, 0, -N/2]},
  "rect_fills": [{"asset": "terrain", "x_min":1,"z_min":1,"x_max":4,"z_max":4,"y_level":1,"rot":0}],
  "cells": [{"asset": "terrain_side", "x":5, "z":1, "y_level":1, "rot":0}],
  "props": [{"asset": "rock_largeA", "x":3.0, "z":2.5, "y_level":1, "scale":1.0}]
}
```

Редактор (`editor.html`) читает/пишет ровно этот же JSON — карта, собранная мышкой, грузится в игру без конвертации (`GameMap.fromJson`).

## ГЛАВНАЯ ЛОВУШКА: Y-span ассета определяет семантику `y_level`

Каждый non-flat terrain-ассет либо **above pivot** (геометрия в `y ∈ [0, +0.5]`, как у ramp — `y_level` = **НИЖНИЙ** уровень), либо **below pivot** (`y ∈ [-0.5, 0]`, как у обычного side — `y_level` = **ВЕРХНИЙ** уровень). Спутать один с другим даёт готовую карту, сдвинутую на целый `level_height` от задуманной.

| Ассет | Y-span | `y_level` = |
|---|---|---|
| `terrain`, все `terrain_road*` | flat (0.0) | сам уровень |
| `terrain_ramp`, `terrain_rampLarge(_detailed)` | above pivot | НИЖНИЙ |
| `terrain_side` | below pivot | ВЕРХНИЙ |
| `terrain_sideCorner` (внешний угол) | above pivot | НИЖНИЙ |
| `terrain_sideCornerInner` (внутренний/вогнутый угол, не протестирован в реальной сцене) | above pivot | НИЖНИЙ |
| `terrain_sideCliff` | above pivot (гибрид: топология оси как у side, но Y-span как у ramp) | НИЖНИЙ |
| `terrain_sideEnd` | above pivot, форма не полностью охарактеризована (есть вертикальная стена в меше) | НИЖНИЙ (осторожно, диагностировать перед использованием) |

**Известный баг в текущем коде** (`mapLoader.ts::heightCellFor`): классификация типа идёт по префиксу строки `asset.startsWith("terrain_side")`. `"terrain_sideCliff".startsWith("terrain_side")` тоже `true` — если `terrain_sideCliff` попадёт в JSON, он провалится в обычную `terrain_side` ветку (`y_level`=ВЕРХНИЙ) вместо нужной `y_level`=НИЖНИЙ семантики. Не баг в проде на 2026-07-07 (`sideCliff` нигде не используется), но если решишь его использовать — сначала добавь отдельный `asset.startsWith("terrain_sideCliff")` чек ПЕРЕД общим `terrain_side` (по образцу того, как `terrain_sideCorner` уже проверяется раньше общего case).

## ЛОВУШКА: один `rot` крутит и меш, и физику heightfield — таблицы обязаны совпадать

`mapLoader.ts` держит отдельные таблицы направления подъёма (`SIDE_ASCENT`, `CORNER_ASCENT`, `RAMP_ASCENT`) для heightfield-математики, а рендер меша просто ставит `inst.rotation.y = rot`. Если таблица кода расходится с реальной ориентацией геометрии — меш едет визуально не туда, куда физически поднимается пол (или наоборот).

**Реальный случай (2026-07-07, ИСПРАВЛЕН, коммит `7b4bb7a`; история — в `docs/space-kit-terrain-catalog.md`):** `RAMP_ASCENT` в `mapLoader.ts` была сдвинута на 90° относительно реальной геометрии `terrain_ramp` (вскрыто vertex-парсингом). Следствие: **нельзя было** подобрать `rot` так, чтобы и меш визуально поднимался в нужную сторону, и heightfield был гладким — при `rot` с гладкой физикой меш вставал поперёк движения («едешь — упираешься в приподнятый блок»). Урок: ramp и side имеют ОДИНАКОВЫЙ ascent basis (+Z при rot=0), обе таблицы теперь идентичны. Если подобное повторится с другим ассетом: чинить таблицу в `mapLoader.ts` по вершинам (не подгонять `rot` в JSON), затем прогнать `tools/scan_heightfield.mjs` (в нём продублирована таблица — синхронизировать!) на затронутых картах до и после.

## sampleHeight — округление к ближайшей клетке

Пробы высоты на границе `±0.5` от центра клетки могут попасть в соседнюю клетку (point-sampled модель, не билинейная интерполяция). Известный артефакт: на стыке `terrain_sideCorner` (диагональный градиент) с соседним осевым `terrain_side` высота расходится до ~0.2м у части границы (сходится к 0 только в самой угловой точке) — не баг ориентации, врождённое свойство модели. Подтверждено `tools/scan_heightfield.mjs` на `arena_slice.json`, симметрично на всех 4 углах. Если понадобится убрать шов — это правка модели градиента в `mapLoader.ts`, не JSON-фикс.

## При любом сомнении о форме/ориентации меша — читай вершины, не гадай

Дважды за проект (Godot-эра и снова в JS-эру) неверная догадка по скриншоту стоила часов работы (`terrain_side` изначально приняли за 3D клин вместо плоского quad). Правило теперь железное:

- `node tools/glb-catalog.mjs [prefix] [--verts]` — бинарный парсер GLB без движка, печатает AABB + классификацию + (с `--verts`) уникальные вершины после XZ-рецентровки для несплошных ассетов. Быстрее чем открывать браузер/Godot.
- Или прямо в браузере: `window.__map`/`window.__scene` (см. скилл `web-slice-workflow`) → `mesh.geometry.attributes.position` для vertex-инспекции живой сцены.
- Обязательные 4 ракурса при визуальной проверке нового ассета/ориентации: top-down (XZ-позиции), низкий iso (наклоны/высоты), вид сбоку строго горизонтально (профиль склона), вид снизу-вверх (есть ли под-сторона/стенки). Один ракурс — гарантированный способ спутать плоское с объёмным.

## Справочник: docs/space-kit-terrain-catalog.md

Полная таблица rot→направление для всех non-trivial ассетов (`terrain_ramp`, `terrain_side`, `terrain_sideCorner`, `terrain_sideCornerInner`, `terrain_sideCliff`), рецепт «юбки» прямоугольного плато (заливка + прямые борта `terrain_side` по кольцу снаружи + диагональные углы `terrain_sideCorner`), правило для рампы-в-юбке (rot берётся из RAMP-таблицы кода, не копируется с соседнего борта — из-за 90°-сдвига выше). Дороги (`terrain_road*`) все плоские (Y-span=0) — коллизии по высоте не боятся, забота только про визуальную стыковку текстуры/декали.

## Редактор карт (`editor.html`)

Страница `http://<LAN-IP>:8090/editor.html`, код `web-slice/src/editor/main.ts`. Управление: СКМ-drag — орбита (OrbitControls), колесо — зум, ЛКМ — поставить выбранный ассет, ПКМ — удалить, `R` — поворот на 90° (цикл `[0,90,180,-90]`), `Q`/`E` — сменить `y_level` (плоскость рейкаста двигается вместе с уровнем), `Esc` — снять выделение. Палитра по категориям (Terrain/Roads/Edges/Props) со статус-баром, который явно подсказывает HIGH/LOW ловушку для выбранного ассета. Export/Import JSON-файла + автосейв в `localStorage`. Кнопка **Drive** пишет карту в `localStorage["editor-drive-map"]` и открывает игру по `/?map=editor` — `main.ts` подхватывает её вместо `public/maps/arena_slice.json` (см. `web-slice-workflow` про синхронизацию `MAP_ASSETS`/`PALETTE`).

Известные ограничения редактора (не баги, MVP-скоуп): пропсы кладутся на плоскость `y_level`, не на реальную высоту рельефа под курсором; нет undo (только ПКМ-удаление); prod build не настроен для двух entry (`index.html`+`editor.html`) — сейчас только dev-режим; панорамирования нет, только орбита вокруг центра.

## Чеклист перед коммитом карты

1. Все non-flat ассеты — `y_level` выставлен по правильной таблице выше (above/below pivot), не наугад.
2. Плоские плитки/дороги стыкуются без зазоров (top-down).
3. `tools/scan_heightfield.mjs <map.json>` — нет разрывов >0.15 между соседними точками через 0.1м (кроме известного corner-seam ~0.2м у самой угловой точки, это ожидаемо).
4. Рампы визуально поднимаются в ту же сторону, что физически (расхождение меша и heightfield = рассинхрон таблицы в `mapLoader.ts` с геометрией, см. кейс RAMP_ASCENT выше — чинить таблицу по вершинам, не `rot` в JSON).
5. Углы плато закрыты корректным ассетом (`terrain_sideCorner` для выпуклых углов, `terrain_sideCornerInner` для вогнутых — последний не протестирован в реальной сцене, гонять через диагностику перед первым боевым использованием).
6. Props не проваливаются под рельеф и не висят в воздухе.
7. Если карта делалась в редакторе — проверить, что все использованные ассеты входят в `MAP_ASSETS` в `main.ts` (иначе плитки молча пропадут при Drive/загрузке).
