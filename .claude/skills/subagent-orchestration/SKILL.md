# Subagent Orchestration

Дистилляция реального процесса миграции на three.js (2026-07-06/07): оркестратор (ты, основная сессия) принимает решения и пишет спеки; агенты (обычно `sonnet`) делают реализацию. Это разделение ролей — не бюрократия, оно ловит ошибки раньше и держит контекст оркестратора маленьким.

## Роли

- **Оркестратор решает, не кодит рутину.** Архитектурные и дизайнерские развилки — твоя работа. Реализация по уже принятому решению — работа агента.
- **Агент реализует по спеке.** Не видит твой разговор с пользователем, не знает истории проекта кроме того, что ты положил в промпт.
- После агента — оркестратор **обязан**: спот-ревью ключевых изменённых файлов (не "доверять и забыть"), `git status` (агенты оставляют мусор — временные файлы, незакоммиченные скретч-скрипты), прогон тестов (`web-slice`: `npx tsc --noEmit && npx vitest run`), коммит с осмысленным сообщением о "зачем".

## Анатомия хорошей спеки агенту

Шаблон, в этом порядке:

1. **Контекст в 2-3 предложения** — что за проект, что за фича, зачем она нужна сейчас. Плюс **явный список файлов, которые агент обязан прочитать первым** (GDD, соседние модули, relevant `.claude/rules/*.md`) — агент не знает, что почитать, если не сказать.
2. **Точная задача** с целевой структурой/интерфейсами, если они уже определены (например: "новый файл `src/weapons/stats.ts` по образцу `src/kart/stats.ts` — registry конфигов, не хардкод").
3. **Жёсткие инварианты и "НЕ ТРОГАТЬ"-список.** Особенно важно при параллельных агентах: каждому агенту — своя непересекающаяся файловая зона. Пересечение зон = гарантированный конфликт при слиянии или тихая порча чужой работы.
4. **Куда класть временные/диагностические файлы** — `tools/` (корень репо) или вне репозитория, НИКОГДА в `web-slice/src/**` (vitest подхватит любой `*.test.ts`, а не-тестовый скретч-файл всё равно замусоривает модульную структуру).
5. **Обязательная самопроверка** перед тем как агент считает задачу законченной: `cd web-slice && npx tsc --noEmit && npx vitest run` — оба зелёные. Если задача не в `web-slice/`, аналогичный gate для того стека (GDScript-синтаксис через headless-хук, если ещё живой Godot-код).
6. **Формат отчёта** — что должен вернуть агент. Обязательный пункт: агент должен **явно перечислить неочевидные решения** ("judgment calls"), которые он принял без явного указания в спеке. Это главный канал, которым оркестратор ловит проблемы на ревью — если агент молчит про судьбоносные развилки, ты о них узнаешь только когда что-то сломается.

При крупной задаче — сначала попросить агента предложить план ДО кода, оркестратор утверждает план, потом агент кодит. Экономит откаты на больших рефакторингах.

## Параллельность

- Независимые файловые зоны → отправлять агентов **одновременно, одним сообщением с несколькими Agent tool calls**.
- Общая файловая зона / зависимые шаги → строго последовательно.
- Делегировал — не делай ту же работу параллельно сам ("не дублируй" из глобального CLAUDE.md).

## Реальные пойманные ошибки агентов (калибровка ревью — пополнять по мере новых находок)

- **Скретч-тестовый файл оставлен в `web-slice/src/` вместо `tools/`** — после параллельного рефакторинга другого агента этот файл сломался (импорты/структура модуля изменились) и завалил `vitest run` для всего проекта, хотя сама фича была не при делах. Урок: явно прописывать "куда класть временное" в каждой спеке, не полагаться на здравый смысл агента.
- **Палитра редактора карт (`editor/main.ts` `PALETTE`) рассинхронизирована со списком preload-ассетов игры (`main.ts` `MAP_ASSETS`)** — агент добавил новый тип тайла в один список и не обновил другой. Карта, собранная в редакторе с этим тайлом, грузилась в игре и **молча** теряла плитку (no error, просто дыра в карте) — тип ошибки, которую тесты не ловят (нет ассерта "все ассеты из палитры есть в MAP_ASSETS"), только визуальная проверка. Урок: при любой правке одного из двух списков — явно попросить агента (или проверить самому) второй список тоже.
- **`RAMP_ASCENT` таблица в `mapLoader.ts` систематически сдвинута на 90° относительно реальной геометрии меша** (обнаружено при построении `docs/space-kit-terrain-catalog.md` независимым vertex-парсингом, не при код-ревью) — таблица была написана "по логике"/аналогии с другим ассетом без проверки по сырым вершинам, хотя `.claude/rules/map-building.md` явно требует vertex inspection для новых ориентаций. Урок: правило "не гадать по скриншоту/аналогии, читать вершины" применяется и когда сам оркестратор/агент пишет код с константами направления, не только при визуальной диагностике в браузере.
- **Агент останавливается на полуслове** («Let me empirically test...», «Now updating the doc:» — и тишина): фоновый агент выдал текст-намерение без tool call и завершился. Работа при этом НЕ доделана, хотя нотификация выглядит как completed. Урок: читать `result` агента критически — если он заканчивается намерением, а не отчётом по запрошенному формату, будить агента через SendMessage с «продолжай, ты остановился на полуслове» (контекст у него сохранён, перезапуск с нуля не нужен). Требование в спеке «формат отчёта» — ещё и детектор недоделанности.
