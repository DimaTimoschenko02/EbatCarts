# Kenney Space Kit — Terrain Asset Catalog

Полный каталог `terrain_*.glb` из `assets/map_materials/space-kit/`, построенный прямым бинарным парсингом GLB (без движка) — см. `tools/glb-catalog.mjs`. Каждый факт в этом документе получен **чтением сырых вершин**, а не догадкой по скриншоту.

Справочник для двух аудиторий: человек, собирающий карту руками в JSON, и будущая AI-сессия, которой нужно быстро понять как ориентировать тайл.

## Как это построено

`node tools/glb-catalog.mjs [prefix] [--verts]` — парсит GLB (header → JSON chunk → BIN chunk), проходит по нодам/мешам, читает `POSITION` аксессоры, применяет полный трансформ ноды (scale → rotation-квaternion → translation — важно: у `terrain_sideCliff` нода имеет `scale=[2,1,1]`, наивный translation-only подход даёт неверный AABB). Для каждого ассета печатает AABB, размер, классификацию и (с `--verts`) уникальные вершины после XZ-рецентровки — той же самой, что `assetLoader.ts`/`recenter_on_import.gd` делают в рантайме/при импорте.

**Важно про систему координат:** raw GLB (glTF, right-handed Y-up) грузится three.js БЕЗ конверсии осей — это тот же coordinate frame, что и в игре. XZ-offset у сырых вершин (обычно ~(2.0, _, 1.5)) — нормальное следствие того, что все ассеты экспортированы из одной Blender-сцены; XZ-рецентровка (three.js: `assetLoader.ts::recenterXZ`, Godot: `recenter_on_import.gd`) это чинит. **Y не трогается нигде** — Y-span "как авторено" это и есть смысловой сигнал (выше/ниже пивота).

## Rotation → направление (по вершинам, rot=0 = как авторено)

Соглашение по повороту (проверено на `terrain_side`/`terrain_sideCorner`, совпадает с уже задокументированным в `.claude/rules/map-building.md`): при объектном `rot=+90°` локальный `+X` уходит в мировой `-Z`, локальный `+Z` уходит в `+X` (стандартная правая Y-rotation матрица, идентична в Godot и three.js — никакой конверсии осей между движками нет).

### `terrain_ramp` / `terrain_rampLarge` / `terrain_rampLarge_detailed`

Низкий край — прямая линия локального `Z=-0.5` (или `Z=-1.0` у Large), высокий (плоская площадка сверху) — `Z ∈ [0, +0.5]` (или `[-0.5,+1.0]` у Large). **Подъём идёт вдоль локального +Z, НЕ вдоль +X.**

| rot | Подъём в |
|---|---|
| 0 | **+Z** |
| 90 | **+X** |
| 180 | **−Z** |
| 270 (-90) | **−X** |

`y_level` = НИЗКИЙ уровень (геометрия above pivot, y∈[0,+0.5]).

### `terrain_side`

Низкий край — `Z=-0.5` (y=-0.5), высокий — `Z=+0.5` (y=0). Подтверждено, совпадает 1:1 с уже задокументированными вершинами в `map-building.md`.

| rot | Подъём в |
|---|---|
| 0 | **+Z** |
| 90 | **+X** |
| 180 | **−Z** |
| 270 (-90) | **−X** |

`y_level` = ВЫСОКИЙ уровень (геометрия below pivot, y∈[-0.5,0]).

### `terrain_sideCorner` (внешний угол)

Диагональный: при rot=0 высокий угол на `(-X,+Z)`. Направление ascent = единичный диагональный вектор к высокому углу.

| rot | Высокий угол в |
|---|---|
| 0 | **−X +Z** |
| 90 | **+X +Z** |
| 180 | **+X −Z** |
| 270 (-90) | **−X −Z** |

`y_level` = НИЗКИЙ уровень (geometry above pivot, как ramp). Совпадает с уже задокументированным в правилах и с `CORNER_ASCENT` в `mapLoader.ts`.

### `terrain_sideCornerInner` (внутренний/вогнутый угол) — новый, не задокументирован ранее

Форма — ИНВЕРСИЯ `sideCorner`: почти весь тайл ВЫСОКИЙ (0.5), низкая — только маленький клин у одного угла. При rot=0 низкий угол на `(+X,-Z)`.

| rot | Низкий угол в |
|---|---|
| 0 | **+X −Z** |
| 90 | **+X +Z** |
| 180 | **−X +Z** |
| 270 (-90) | **−X −Z** |

Использовать для вогнутых углов L-образного/ступенчатого плато (там где периметр "заходит внутрь"). **Не протестировано в реальной сцене** — перед использованием прогнать через диагностическую сцену/JSON, как требует чеклист в `map-building.md`.

### `terrain_sideCliff` — гибридная форма, требует отдельной обработки в коде

Общая форма ОСЕВАЯ (не диагональная) — совпадает по топологии с `terrain_side` (низкий край — прямая линия, высокий — прямая линия, никакого диагонального угла), НО:
- **Y-span above pivot** (y∈[0,+0.5]) — как у `ramp`/`sideCorner`, а не below pivot как у обычного `side`
- Низкий край имеет декоративную выемку (доп. вершина на полпути, `(0, -0.375)` вместо ровной `-0.5`) — чисто визуальная деталь, не влияет на общий уклон

При rot=0: низкий край на `Z=-0.5`, высокий на `Z=+0.5` — **та же rotation-таблица что у `terrain_side`**, но с семантикой `y_level` = НИЗКИЙ (как ramp), не ВЫСОКИЙ.

| rot | Подъём в |
|---|---|
| 0 | **+Z** |
| 90 | **+X** |
| 180 | **−Z** |
| 270 (-90) | **−X** |

**⚠️ Ловушка в текущем коде mapLoader.ts:** `heightCellFor()` определяет тип по префиксу строки: `asset.startsWith("terrain_side")` — а `"terrain_sideCliff".startsWith("terrain_side")` тоже `true`! Если `terrain_sideCliff` когда-нибудь попадёт в JSON карты, он полностью провалится в ветку `terrain_side` (обычный side) и получит `y_level=ВЫСОКИЙ` семантику вместо нужной `y_level=НИЗКИЙ` — итоговая высота будет сдвинута на целый `level_height` (0.5м) от реальной геометрии. **Сейчас это не баг в проде** (sideCliff нигде не используется в `arena_slice.json`), но если решите его использовать — нужен отдельный `asset.startsWith("terrain_sideCliff")` чек ПЕРЕД общим `terrain_side` чеком (по аналогии с тем как `terrain_sideCorner` уже проверяется раньше). Это src-изменение, не делал в рамках этой задачи.

### `terrain_sideEnd` (конец полуострова) — не полностью охарактеризован

Форма явно асимметрична (не диагональная, не простая ось) — обнаружены вершины с ОДИНАКОВЫМИ (x,z), но РАЗНЫМИ y (например `(0, y=0, z=0.5)` и `(0, y=0.5, z=0.5)` одновременно) — это означает **вертикальную стену/обрыв** где-то в мешe (вероятно торцевая "обрывистая" грань полуострова), не просто наклонную плоскость. Y-span above pivot (ramp-like), но точную rotation-таблицу пока не вывожу с уверенностью — сырых вершин слишком много и топология не тривиальна.

**Рекомендация:** прежде чем использовать — прогнать через `scenes/asset_diag.tscn` (Godot) или создать эквивалентную three.js диагностическую страницу, посмотреть с 4 обязательных ракурсов (top-down, low iso, side, from-below) как требует чеклист в `map-building.md`. Не входит в текущий `arena_slice.json`.

## Правила сочетаемости

### Дороги (`terrain_road*`)

Все плоские (Y-span=0), отличие только в декали/текстуре:
- `terrain_roadStraight` — прямой участок, ориентация текстуры вдоль локального Z; для дороги вдоль мировой оси X нужен `rot=90`.
- `terrain_roadCorner` — L-поворот, `rot` = 0/90/180/270 в зависимости от того к каким двум соседним сторонам должна повернуть дорога.
- `terrain_roadCross` — перекрёсток на 4 стороны, `rot` не важен (симметричен по 4-fold).
- `terrain_roadEnd` — тупик (дорога переходит в terrain), rot ориентирует "открытую" сторону.
- `terrain_roadSplit` — T-образный перекрёсток (3 стороны), rot ориентирует какая сторона "закрыта".

Так как всё плоское, дороги можно класть где угодно без риска коллизии по высоте — единственная забота это визуальная стыковка текстуры между соседними плитками.

### Юбка плато (skirt) — прямоугольное плато N×M на уровне 1

Рецепт для плато `x_min..x_max, z_min..z_max` на `y_level=1` (level_height=0.5):
1. **Заливка плато:** `rect_fills` — `terrain`, `y_level=1`, весь прямоугольник.
2. **Прямые борта** (`terrain_side`), по одному кольцу СНАРУЖИ прямоугольника (`x_min-1`/`x_max+1`/`z_min-1`/`z_max+1`), `y_level=1` (ВЫСОКИЙ — соответствует плато):
   - Северная сторона (`z = z_min-1`, `x` от `x_min` до `x_max`): `rot=0` (спуск в −Z, наружу от плато)
   - Южная (`z = z_max+1`): `rot=180`
   - Западная (`x = x_min-1`): `rot=90`
   - Восточная (`x = x_max+1`): `rot=270` (он же `-90`)
3. **Внешние углы** (`terrain_sideCorner`), `y_level=0` (НИЗКИЙ — в отличие от прямых бортов!), в 4 угловых клетках кольца (`x_min-1,z_min-1` и т.д.):
   - NW-угол (`x<x_min`, `z<z_min`): `rot=90`
   - NE-угол (`x>x_max`, `z<z_min`): `rot=0`
   - SE-угол (`x>x_max`, `z>z_max`): `rot=270` (`-90`)
   - SW-угол (`x<x_min`, `z>z_max`): `rot=180`

**Известный геометрический артефакт (не баг, ограничение модели):** т.к. `terrain_sideCorner` использует ДИАГОНАЛЬНЫЙ height-градиент, а соседние `terrain_side` — ОСЕВОЙ, на стыке угла с прямым бортом высота field'а не совпадает идеально (расхождение до ~0.2м на части границы, сходится к 0 только в самой угловой точке). Подтверждено скан-тестом (`tools/scan_heightfield.mjs`) на текущей `arena_slice.json` — расхождение симметрично на всех 4 углах, значит это не ошибка ориентации, а врождённое свойство "point-sampled arcade heightfield" подхода (см. комментарий в `mapLoader.ts`). Визуально может быть заметно как лёгкая "ступенька"/шов у самого угла плато — если понадобится убрать, это требует изменения модели градиента в `mapLoader.ts` (не JSON).

### Заезд (ramp) в юбке

Рампа заменяет 1-2 клетки прямого борта (создаёт разрыв в кольце), давая пологий спуск с уровня `N` на уровень `N-1`:
- `y_level` рампы = НИЗКИЙ уровень (`N-1`)
- Рампа должна располагаться в том же "кольце", что и борта, которые она заменяет — т.е. если западный борт на `x=x_min-1`, то и западная рампа на том же `x=x_min-1`.
- **С 2026-07-07 `RAMP_ASCENT` идентична `SIDE_ASCENT`** (см. ниже — баг пофикшен), так что теперь **rot рампы можно просто скопировать с rot соседнего борта** того же направления подъёма — они используют одну и ту же таблицу.

Файл: `web-slice/src/map/mapLoader.ts` (после рефакторинга — раньше был `src/game/mapLoader.ts`, идентичный).

| Таблица | Совпадает с вершинами? |
|---|---|
| `SIDE_ASCENT` | ✅ Полностью совпадает. Базисное направление подъёма из вершин (+Z при rot=0) даёт ровно ту же таблицу, что уже в коде. |
| `CORNER_ASCENT` | ✅ Полностью совпадает (комментарий в коде "verified by vertex read in browser" подтверждается независимо). |
| `RAMP_ASCENT` | ✅ **Пофикшено.** До 2026-07-07 таблица была сдвинута на 90° от реальной геометрии (`{0:[1,0], 90:[0,-1], 180:[-1,0], 270:[0,1]}` вместо правильной `{0:[0,1], 90:[1,0], 180:[0,-1], 270:[-1,0]}`) — меш визуально ascend-ил перпендикулярно направлению движения, хотя heightfield был гладким. Исправлено в `mapLoader.ts` (таблица теперь идентична `SIDE_ASCENT`), `mapLoader.test.ts` (тест на rot=0 переписан под +Z, добавлен тест на rot=90→+X), `arena_slice.json` (западная рампа `rot=0→90`, восточная `rot=180→-90`) и `tools/scan_heightfield.mjs` (дублирующая таблица обновлена в паре с src). |

### Что это значит на практике

`heightCellFor()` (физика/heightfield) и рендер-меш (`inst.rotation.y = rot`) используют **один и тот же** `rot` — но т.к. таблица физики для рампы рассинхронизирована с реальной геометрией на 90°, **невозможно одним значением `rot` одновременно** (а) сделать меш визуально ascend-ящим в правильную сторону, И (б) сделать heightfield физически гладким (без разрыва высоты на границе с соседними плоскими клетками.

Проверено эмпирически (`tools/scan_heightfield.mjs`, реплицирует формулу `heightCellFor`/`sampleHeight` 1:1):
- Текущие ramp-клетки в `arena_slice.json` (запад `rot=0`, восток `rot=180`) дают **идеально гладкий heightfield** (0→0.5 плавно, без разрывов, совпадает со соседями) — физика уже верна.
- НО при этом рендер-меш (реальная геометрия) при `rot=0` восходит вдоль **+Z** (перпендикулярно направлению движения запад→восток), а не вдоль +X, как "думает" heightfield. Т.е. визуально плитка рампы будет выглядеть как приподнятый блок/ступенька поперёк пути, а не как гладкий скат по ходу движения — это ТОЧНО соответствует жалобе "едешь — упираешься в высокий край".

**Это баг уровня кода (`RAMP_ASCENT` в `mapLoader.ts`), не карты.** Пофиксить его одной правкой `rot` в JSON нельзя — если повернуть рампу так, чтобы МЕШ визуально ascend-ил верно (запад: `rot=90`, восток: `rot=270`), то heightfield-таблица (`RAMP_ASCENT[90]=(0,-1)`, `RAMP_ASCENT[270]=(0,1)`) начнёт зависеть от Z вместо X — и создаст РЕАЛЬНЫЙ разрыв высоты (invisible wall) на границах с плоскими соседями. Корректный фикс — исправить саму таблицу в `mapLoader.ts`:

```
const RAMP_ASCENT: Record<number, [number, number]> = {
  0: [0, 1], 90: [1, 0], 180: [0, -1], 270: [-1, 0],
};
```

(=ровно таблица `SIDE_ASCENT`, что логично — обе геометрии имеют одинаковый базис подъёма +Z при rot=0). Не стал вносить эту правку сам — задача явно требовала не трогать `web-slice/src/**`; эскалирую `lead-programmer`/`gameplay-programmer` для решения.

## Скрипт

`tools/glb-catalog.mjs` — `node tools/glb-catalog.mjs [prefix] [--verts]`. По умолчанию `prefix="terrain"` (все terrain-ассеты). `--verts` печатает уникальные вершины после XZ-рецентровки для несплошных (не-flat) ассетов — полезно для быстрой проверки нового rot-направления без запуска Godot/three.js.

`tools/scan_heightfield.mjs [путь-к-map.json]` — реплицирует формулу `heightCellFor`/`sampleHeight` из `mapLoader.ts` (дублирует вручную — держать в синхроне, если код изменится) и сканирует всю карту на предмет разрывов высоты (>0.15 между соседними точками через 0.1м) — быстрый способ находить "invisible walls" без визуального тестирования в браузере.
